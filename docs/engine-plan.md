# Sol Engine — Development Plan

Working name: **Sol Engine** (placeholder). A from-scratch C++20 engine purpose-built for one game: **Sol**, a single-player 3D space sandbox (see `docs/gdd.md`). This is not a general-purpose engine; every system exists to serve that game.

Companion documents: `AGENTS.md` (working rules), `docs/gdd.md` (game design). When this plan and reality diverge, update this plan in the same change set.

---

## 1. Goals & Constraints

- **From scratch.** Platform layer, math, renderer, ECS, asset pipeline, UI — written in-repo. Approved exceptions (see `AGENTS.md` §5): Vulkan SDK, glslang (build-time), Lua 5.4, Dear ImGui (dev tools only).
- **Windows first, portable by design.** Win32 + Vulkan initially; no Win32 lock-in outside the platform layer so a Linux backend can be added later without surgery.
- **Single-player only.** No networking layer. The simulation can be tightly integrated with the client; we still keep sim/render decoupled for correctness, not for netcode.
- **Vulkan only.** One graphics backend, wrapped in a thin RHI so renderer code stays clean — not to support other APIs.
- **Data-driven and scriptable from early on.** Content in data files, game logic in Lua. Modding falls out of this for free.
- **C++20, exceptions off, RTTI off, warnings-as-errors.**

### The space-scale constraint (day one, non-negotiable)

Space games die on floating-point precision. `float` runs out of useful precision a few kilometers from origin; star systems are millions of kilometers across.

- **Simulation positions are 64-bit** (`double` in a `DVec3`; revisit fixed-point only if evidence demands it).
- **Rendering is camera-relative**: every frame, world positions are rebased against the camera (or a floating origin) before conversion to `float` for the GPU. The GPU never sees large coordinates.
- **Hierarchical coordinates**: galaxy (system id + light-year offsets) → system (double meters from system barycenter) → local/attached frames (e.g., docked at a station). Only the active system is simulated at full fidelity.

Every system that touches transforms must respect this from its first commit.

## 2. Architecture

Strict layering; a module depends only on layers below it.

```
┌─────────────────────────────────────────────────────┐
│  game/          C++ glue, game states, Lua scripts   │
├─────────────────────────────────────────────────────┤
│  engine/                                             │
│   ui         game UI (HUD, map, menus) [later phase] │
│   scripting  Lua VM, bindings, hot-reload            │
│   sim        flight, collision, economy, AI host     │
│   ecs        entities, components, systems, queries  │
│   assets     runtime asset loading, hot-reload       │
│   renderer   scene rendering, materials, passes      │
│   rhi        thin Vulkan wrapper                     │
├─────────────────────────────────────────────────────┤
│   platform   window, input, filesystem, time, dylib  │
│              (win32/ backend now, linux/ later)      │
├─────────────────────────────────────────────────────┤
│   core       math, memory, containers, jobs,         │
│              log/assert, events, serialization       │
└─────────────────────────────────────────────────────┘
tools/cooker/   offline asset compiler (own executable)
```

### 2.1 Platform layer (`sol::platform`)

Window creation, input (keyboard/mouse first; gamepad/HOTAS later), filesystem paths + file IO + change watching (for hot-reload), high-resolution clock, dynamic library loading. Portable API in public headers; `win32/` implementation selected at compile time (no virtual dispatch needed — one backend per build). Sits directly above `core` (uses its math/log/assert). Sanctioned platform-specific touch points outside this module: Vulkan surface creation (`engine/rhi/src/win32/`) and the ImGui platform backend bridge (`engine/ui/src/win32/`).

### 2.2 Core layer (`sol::core`)

- **Math**: `Vec2/3/4`, `Mat3/4`, `Quat`, plus `DVec3`/`DQuat` for sim-space; transforms, intersection primitives (ray/sphere/OBB/frustum), SIMD-friendly layout (SSE where it pays, scalar fallback). Column-major, right-handed, -Z forward (decide once, document in the header, never revisit). Fully unit-tested — this is the foundation everything trusts.
- **Memory**: linear/arena allocator (per-frame scratch), pool allocator, tracking wrapper for leak/usage reporting in dev builds. `std` containers with custom allocators where std suffices; bespoke containers only when profiling justifies them.
- **Job system**: work-stealing thread pool, job handles with dependencies, parallel-for. Sized to (hardware threads − 1); main thread can pump jobs while waiting.
- **Logging/assert**: leveled logging with compile-time stripping, `SOL_ASSERT` (dev) / `SOL_VERIFY` (always), crash-time log flush.
- **Events**: small synchronous event bus for engine signals (window resized, device lost, asset reloaded). Gameplay events go through sim/Lua, not this.
- **Serialization**: binary reader/writer with versioning for cooked assets and save games; a small TOML parser for human-authored data (written in-repo — it's a weekend-sized, well-specified format).
- **Hashing/ids**: FNV-1a string hashing, `StringId` for interned names, stable asset ids.
- **PRNG**: splitmix64/xoshiro-family generators with explicit streams — procgen determinism depends on never sharing generator state between systems.

### 2.3 RHI (`sol::rhi`)

A thin, Vulkan-only abstraction — its job is to make renderer code short and safe, not to hide Vulkan:

- Instance/device/queues bootstrap, validation layers in dev builds.
- Swapchain with resize/recreate handling.
- Resources: buffers, images, samplers with VMA-style sub-allocation (written in-repo: a simple block allocator over `vkAllocateMemory` first; grow sophistication as needed).
- Pipelines and shader modules (SPIR-V in), pipeline cache.
- Bindless-leaning descriptor management (large descriptor arrays + push constants) to keep material binding simple.
- Command recording per frame with N-buffered frame contexts, timeline-semaphore based sync.
- Deletion queue for safe resource destruction.

Later: a render-graph layer for pass scheduling/barriers once pass count justifies it (Phase 4+, not before).

**Shader toolchain**: GLSL → SPIR-V via glslang at build time (CMake custom commands); dev builds can also compile at runtime for shader hot-reload.

### 2.4 Renderer (`sol::renderer`)

Built on the RHI, consumes ECS render components:

- Forward+ (clustered forward) lighting — space scenes are mostly one dominant star light + point lights (engines, weapons); clustered forward keeps transparency (shields, glass, nebulae) simple. HDR pipeline with physically-plausible exposure + tonemap.
- PBR materials (metal/rough), normal mapping; emissive is a first-class citizen (engine glow, windows, weapon fire).
- Sky: procedural starfield + milky-way band rendered to a cubemap per system seed; distant planets/stars as impostors.
- Planet/star rendering: scaled-space impostors first (planets are scenery, not landable — see GDD non-goals); atmosphere shader later.
- Particles for thrusters, impacts, explosions (GPU-sim in a later phase; CPU first).
- Debug draw (lines, shapes, text) from day one — space is empty and dark; you cannot debug what you cannot see.
- Camera-relative transform flow: sim `DVec3` → subtract camera origin → `float` model matrices → GPU.

### 2.5 ECS (`sol::ecs`)

Custom ECS with **sparse-set storage** — chosen via the Phase 3 spike benchmark of our actual access patterns (thousands of ships/projectiles iterated linearly per sim tick, sparse component churn on projectiles); see `docs/decisions/001-ecs-storage-model.md` for the numbers and the archetype comparison.

- Entities are generational handles. Components are plain structs (POD-leaning, serializable).
- Systems are free functions scheduled explicitly (fixed order first; job-graph parallelism later, using the core job system).
- Queries/views for iteration; deferred structural changes via command buffers so systems can run in parallel safely.
- The ECS is the save-game backbone: world state serialization walks component storage.

### 2.6 Asset pipeline (`tools/cooker` + `sol::assets`)

- **Cooker** (separate executable, links `core` only): imports source assets → engine-native binary formats with stable asset ids + a pack manifest. Importers written in-repo: glTF (JSON + buffers) for meshes, PNG for textures (→ BCn-compressed at cook time; BCn encoder in-repo, quality over speed initially), WAV for audio (later), TOML/JSON data defs → validated binary tables. *(Phase 5 update: data defs load as strictly-validated TOML at runtime (`sol::assets::DefDatabase`) — validation happens at load either way and runtime parsing is what makes def hot-reload cheap; cooking defs to binary tables joins the pack/manifest work in Phase 7.)*
- **Runtime** (`sol::assets`): async loading via the job system, handle-based registry, reference counting, **hot-reload in dev builds** (file watcher → recook → swap) for textures, meshes, shaders, data defs, and Lua scripts. Fast iteration is the single biggest force multiplier for a solo/small team — treat hot-reload as a feature, not a luxury.

### 2.7 Simulation (`sol::sim`)

- **Fixed timestep** (start at 60 Hz sim tick), accumulator loop, render interpolation between sim states. Sim never reads wall clock.
- **Flight model**: Newtonian 6-DoF (force/torque integration) with layered flight assists (velocity damping, rotation damping, speed limiter) — "Newtonian under the hood, flyable by default," Elite-style. Assist-off mode is free.
- **Collision**: custom broadphase (uniform grid or sweep-and-prune per local bubble) + narrowphase (sphere, capsule, OBB, and convex-hull vs. ray for hit-scan). Ships are rigid bodies with simplified collision response — this is a space game: no stacking, no contact manifolds resting on floors. A full physics library is explicitly out of scope.
- **Simulation LOD (the living universe)**: the player's current system runs the full sim ("bubble"). Everything else runs a coarse agent simulation — ships as schedule entries moving between markets, battles resolved statistically — promoted to full fidelity when the player arrives. This is the EVE/X4 trick and it is an architectural commitment: every gameplay system (economy, AI, missions) must define both its full-fidelity and coarse representations.
- **Economy sim**: agent-based — stations produce/consume goods, NPC traders haul, prices from local supply/demand. Runs on the coarse layer galaxy-wide; ticks slower than the physics sim (e.g., 1 Hz coarse, minutes-scale for economy).

### 2.8 Scripting (`sol::scripting`)

- **Lua 5.4** vendored, exceptions-off friendly (compiled as C, longjmp error handling contained at the boundary).
- Hand-rolled binding layer (no sol2): a small template-based registration API for exposing C++ functions/types + a typed handle scheme for entities/assets crossing the boundary. Bindings are explicit and audited — the Lua↔C++ surface is the engine's public API and the mod API.
- **What lives in Lua**: mission logic, faction AI decision-making (strategy layer), economy tuning/rules, event scripting, UI flow, ship/weapon/faction stat definitions (via data files Lua can also generate).
- **What stays in C++**: per-tick hot loops (physics integration, collision, individual ship steering execution), rendering, ECS internals.
- Script hot-reload with state-preserving reload where feasible.
- **Mod loading**: mods are directories (data + scripts) layered over base content by load order. Same mechanism the base game uses — the base game is "mod zero."

### 2.9 UI

- **Dev/debug**: Dear ImGui from Phase 2 — perf HUD, entity inspector, sim controls, economy dashboards, console. Never ships as player-facing UI.
- **Game UI** (Phase 8d): custom immediate-mode framework over a batched screen-space quad renderer — HUD (targeting reticles, velocity indicators, shield/hull), menus, station screens; map screens (system + galaxy) rode along with the exploration item and landed in Phase 8e. Text comes from an in-repo TrueType rasterizer, baked to atlases by the cooker. **Revision**: screens are authored in C++ for v1; the original "driven from Lua for layout/flow" intent is deferred to a later modding pass, once the widget vocabulary has stopped moving (a Lua binding over a churning API is wasted work). C++ was always the drawing side; this only defers the layout/flow half.

### 2.10 Audio (later)

WASAPI backend behind a platform interface, mixing in-engine, WAV/ogg (stb_vorbis-class decoder written or approved later — flagged as a future dependency decision). Scheduled Phase 8; stubbed interface earlier so gameplay code can post sound events into a void.

#### Phase 8a — Outfitting, Progression & Purchasing ✅ (completed 2026-08-15)

Implements GDD §8 Outfitting **[core]** plus the two decisions that live here: the trivial crew system (`decisions/006`) and the death-penalty insurance/hardcore rules (`decisions/007`).

**Data model (assets layer).** New strict-schema def types in `game/data`:
- `[[module]]` — `id`, `name`, `slot` ∈ {`shield`, `engine`, `cargo`, `utility`}, `price`, `mass` (kg), `power_draw`, and stat modifiers.
- `[[crew]]` — `id`, `name`, `role`, `price` (one-time hire fee), and stat modifiers (no mass/power — crew occupy berths, not slots).
- Modifier vocabulary shared by modules and crew: `<stat>_add` and `<stat>_mul` keys over a fixed stat list (`forward_accel`, `reverse_accel`, `lateral_accel`, `vertical_accel`, `max_speed`, `turn_rate` (uniform over all three axes), `cruise_speed_scale`, `shield_strength`, `shield_regen`, `armor`, `hull`, `weapon_capacitor`, `weapon_recharge`, `cargo`). Unknown keys are schema errors, per the Phase 5 defs contract.
- `[[ship]]` gains `price`, `mass`, `power_output`, per-type slot counts (`slots_shield`, `slots_engine`, `slots_cargo`, `slots_utility`), and `crew_berths`. `[[weapon]]` gains `price`.

**Loadout resolution (assets layer, `sol::assets` `loadout.hpp`).** Pure function: base `ShipDef` + fitted modules + crew → effective `ShipDef`. Order-independent math: all `_add` modifiers sum onto the base, then all `_mul` multiply, then the mass penalty scales linear/angular accelerations by `mass / (mass + Σ module mass)`. Validation rejects a fit that overflows any slot count, the crew berths, or the power budget (`Σ power_draw ≤ power_output`). Lives in assets (below sim) so the game applies effective defs through the existing `applyShipDef` path unchanged; unit-tested like all def machinery (parsing, ordering, budgets, determinism).

**Weapons.** The single weapon mount becomes part of the fit: the fit stores a weapon id (initialized from the ship def), stations sell weapons, and swapping is outfitting like any module. Multiple hardpoints are **out of scope** until combat supports more than one `ShipWeapon`.

**Fleet & purchasing (game layer).** The player owns a fleet: each owned ship records its def id, weapon, fitted modules, hired crew, and where it is (active, or stored at a specific station). Buy ships and modules while docked; sell-back at a flat resale fraction. Switching ships happens only while docked at the station where the target ship is stored; the current ship stays stored there. Cargo remains player-global; a switch that would strand cargo over the new ship's capacity is refused. v1 availability: every station sells every ship/module/weapon/crew def (region- and faction-gated catalogs arrive with the faction item).

**Death (decisions/007).** Default: respawn at last dock in the same ship + fit + crew, cargo lost, deductible = fixed fraction of (hull price + fitted module and weapon prices) charged, clamped at zero credits. Hardcore: new-game flag (`--hardcore`), stored in the save header; death deletes the save and starts a fresh run. Deductible fraction and resale fraction are game-side constants for now (tuning levers; move to data when a settings def exists).

**UI & console.** The docked ImGui screen grows Shipyard / Outfitting / Crew tabs beside Trade (still the provisional dev UI — the custom game UI is its own Phase 8 item). Console API: `sol.modules`, `sol.crew_defs`, `sol.fit`, `sol.fleet`, `sol.buy_module`, `sol.sell_module`, `sol.buy_weapon`, `sol.buy_ship`, `sol.sell_ship`, `sol.select_ship` (fleet indices 1-based), `sol.hire_crew`, `sol.fire_crew`, `sol.insurance_quote`.

**Save v4.** Header gains the hardcore flag; body gains the fleet (active index; per ship: def id, weapon id, module ids, crew ids, stored system/station). On load the active fit re-resolves and re-applies, so def edits between sessions land coherently (same rule as hot-reload).

✅ *TrueType reader + rasterizer* (`sol::assets::TrueTypeFont`, 2026-08-16) — the deepest technical risk in this phase, taken first because it is font-choice-independent. Reads `head`/`maxp`/`hhea`/`hmtx`/`loca`/`glyf`/`cmap` (formats 4 and 12) plus format-0 `kern`, resolves composite glyphs under nested 2×3 transforms, and rasterizes with a signed-area cell accumulator — analytic coverage, no supersampling. Collections (`ttcf`) and CFF outlines (`OTTO`) are rejected with a clear message rather than misparsed, and every reader path is bounds-checked so a truncated file fails the parse instead of reading past the end. 12 tests (assets suite 13 → 25, 70 → 82 overall) build their own font byte by byte in the test — no asset to license, and a failure indicts the reader rather than a mystery file — covering metrics, cmap lookup and misses, simple/composite outlines, hole winding, antialiasing, small sizes, malformed input, and byte-identical repeat rasterization (the property the cooked atlas depends on). Eyeballed against real Windows fonts (Arial `A`/`g`/`Á`, Segoe UI at 11 px) via a throwaway ASCII-art probe: correct shapes, counters, accents, and edge coverage.

✅ *Runtime font, UI renderer, and DrawList — first pixels on screen* (2026-08-16). `sol::assets::Font` loads `.sfont`, resolves styles by name and glyphs by codepoint (binary search over a style's run), measures UTF-8 runs, and validates hard: the draw path indexes glyph rects without checking, so records are validated into locals and committed only on success — a rejected asset leaves an empty font, not a half-populated one. `sol::renderer::UiRenderer` draws batched, tinted, scissor-clipped quads in pixel space (`shaders/ui.vert|frag`, `ParticleRenderer` buffer pattern, alpha blend, no depth test). The glyph atlas is uploaded R8 with a `(1,1,1,R)` view swizzle — a small `TextureUploadDesc` extension — so coverage lands in alpha and text shares one shader with solid fills, which a 1×1 white pixel in texture slot 0 provides. `sol::ui::DrawList` builds the geometry: rects, outlines, rounded rects, lines, triangles, clipped text with box alignment, an intersecting clip stack, and batch merging that only breaks on a texture or scissor change. 16-bit indices make its capacity a correctness limit, so overflow refuses to emit and raises a flag rather than wrapping. **New `ui.unit` suite** (suites 6 → 7): 14 headless tests over batching, clip intersection, degenerate input, text advance and alignment, atlas UVs, overflow, and index validity. Wired into the game: `SceneRenderer` loads the font, registers the atlas, and draws the list after tonemap and before `DevUi`, and `game/src/game_ui.cpp` builds the first real surface — a flight panel with the system name in Plex SemiBold 32, speed, a flight-mode tag, and hull/shield meters. *Verified live: the panel renders in-game reading "Lyrioa", tracks state (CRUISE lights up, range ticks 800 m → 616 m), agrees with the dev HUD beside it, and validation is clean — the first pipeline bug found this way was the UI pipeline declaring no depth attachment while the present pass carries one.*

✅ *Widget framework and menu shell* (2026-08-16). `sol::core::fnv1a`/`hashCombine` land in core (plan §2.2's hashing line, previously unbuilt) and give widgets identity: `UiContext` hashes an id stack, so the same label in two panels or two rows never collides. The context carries a `Theme` (colors, metrics, font style names — a restyle is a data change), an `InputState` the game fills from the platform layer, and retained hover/active/**focus** state. Widgets take explicit rects and report what the player did: label, panel, button, checkbox, slider, selectable, meter. `layout.hpp` adds `Column`/`Row` cursors that hand out rectangles — deliberately not a flex engine. **Keyboard operation is real, not aspirational**: Tab/arrows cycle focus (wrapping, skipping disabled widgets, dropping focus when a widget disappears), Enter/Space activate, arrows step sliders. Focus advances at `endFrame`, when the full widget order is known.

**Menu shell** (`game/src/menu_screens.cpp`): the game now **boots to a main menu** instead of straight into the cockpit — title, tagline, New Game / Continue (disabled without a save) / Settings / Quit, and a hardcore checkbox, so `--hardcore` is no longer command-line-only. Esc opens a pause menu (Resume / Save / Load / Settings / Quit); a menu **stops the sim clock**, so unpausing does not fast-forward the galaxy. Settings (UI scale, mouse sensitivity, invert pitch, vsync) persist to `settings.toml` beside the save — deliberately *not* in the save file, so a settings change can never risk a run — and a stale or malformed file falls back to defaults per key rather than blocking startup. `main.cpp` grows an explicit `GameState`, and every gameplay key now reads through a guard so Tab means "next widget" in a menu and "cruise" in flight. **UI scale** is implemented properly: the UI is built against a virtual screen of (pixels ÷ scale) and stretched back, with layout, cursor, and scissor all converted together. `platform::Window` gains `mousePosition()`.

*Verified live: boots to the menu with the sim frozen at tick 0; Tab moves a visible focus ring; New Game enters flight; Esc opens the pause menu; Settings drags to 1.85 and toggles a checkbox; Back writes `settings.toml`; a full restart reloads those values and the whole UI is visibly 1.85× larger. Three real bugs came out of driving it: the docked-state sync re-derived from a stale frame-start flag and slammed the pause menu shut on the frame it opened; the swapchain is an `_SRGB` format, so sRGB-authored colors wrote out far too bright until the shader converted them; and clip rectangles were being clamped in virtual pixels against a real framebuffer, cropping the scaled UI. 33 `ui.unit` tests (14 draw-list, 13 context, 6 layout) plus 5 new core hash tests; 7 suites green, zero warnings.*

✅ *Station screen* (2026-08-16). #### Phase 8e — Exploration, Scanning & Map Screens ✅ (completed 2026-08-16)

Implements GDD §8 Exploration & scanning **[likely]** — "unvisited systems are unknown; scanning reveals bodies, signals, derelicts, hidden caches; the fringe pays explorers" — and pays the debt Phase 8d deferred: the **system and galaxy map screens**, which this item has to build anyway and is the first item that knows what they must show.

Scope decided with the user: the scan is **two verbs and no minigame** — a ship-wide *pulse* that reveals contacts and a *target scan* that resolves one; exploration pays through **sellable survey data** and **derelict/cache loot**, and deliberately *not* through remote market intel or survey contracts (both stay open — see Out of scope); fog of war is **soft** — a gate names where it leads, a system's contents stay blank until you have been there, and nothing anywhere is *refused* for being unknown; and both maps ship with route plotting but **no auto-jump** (`decisions/005` — you fly every leg yourself, which is what makes the fringe far away).

**Knowledge & survey state (`sol::sim::SurveySim`, coarse layer).** A fourth sibling of `Economy`/`FactionSim`/`MissionSim` in `engine/sim/survey.hpp`, and it earns that place the same way they do: it is the part that must be deterministic, unit-testable, and saved. It holds one `SystemKnowledge` per system — `Unknown` → `Charted` (name, map position, and lanes known because a gate you have stood at points here) → `Visited` (you have been in the system: stations, bodies, and owner are known) → `Surveyed` (every body scanned and every signal resolved) — plus, per system, which signals have been discovered, resolved, and emptied, and a **survey ledger** of unsold data entries. Transitions are one-way and driven by events the game reports (`notifyArrival`, `notifyBodyScanned`, `notifySignalResolved`), exactly the `MissionSim` shape. Charting is a pure consequence of arrival: entering a system charts every system its gates lead to, so the map grows outward along the lanes you actually travel.

**Signals (deterministic content, not entities-on-disk).** A system's signals are a pure function of `SystemSpec::seed` and `SurveyParams`, generated on demand by `signalsFor(galaxy, systemIndex, out)` — the same trick the galaxy generator uses, so the save stores per-signal *state* (discovered/resolved/emptied bits) and never the content. Count and richness follow the GDD's region gradient (core 0–2, frontier 2–4, fringe 3–6), and positions cluster in the playfield around the primary planet like stations and gates do, inside the `decisions/005` cruise budget. Two kinds in v1: **derelict** (a dead hull — commodity cargo, sometimes a module) and **cache** (a stash — cargo plus credits). Both are *sites you fly to and empty*, not wrecks you cut apart: **full salvage — hull cutting, wreck fields left behind by real battles — belongs to the mining/salvage item**, and this spec deliberately stops at "open the container" so the two items do not build the same thing twice.

**The scan loop (bubble layer, `SpaceWorld`).** Two verbs, both range-gated by the fitted scanner:
- **Pulse** (`R`, a cooldown, no hold): reveals every undiscovered signal within `scanRange` of the ship as an unresolved contact — a bearing and a range, nothing more. Sweeping a whole playfield takes several pulses from several places, which is the exploration loop: you fly, you pulse, you fly.
- **Target scan** (no key): a discovered-but-unresolved contact, or an unscanned celestial body, that is the current target and within `scanTargetRange` accumulates scan progress while it stays targeted and roughly boresighted; at 100% it resolves — the contact becomes a named nav target with a kind, a body becomes surveyed — and the resulting data lands in the ledger.
- **Empty** (`G` — the existing interact key): within `kSalvageRange` of a resolved site with nothing left to dock at, the dock prompt slot reads `[G] SALVAGE` and one press moves the site's contents into the hold (clamped to cargo space; a partial take leaves the rest). This reuses the verified dock-prompt and cargo paths rather than inventing a second interaction.

Discovered signals join `m_targets`, so `T`-cycling, the autopilot (`F`), and the HUD target readout all work on them with no new machinery.

**Payoff: survey data.** Every resolution writes a `SurveyEntry` into the ledger — system, kind (system arrival, body, site), region, and a **first-discovery** flag — and the ledger is sold at any station: a seventh **Survey** tab on the station screen lists unsold entries with their value and a Sell All, and the credits land like a trade. Value comes from `SurveyParams` (base per kind × region multiplier × first-discovery bonus, plus a completion bonus the first time a system reaches `Surveyed`), so "the fringe pays explorers" is a tuning table, not a hard-coded curve; selling also pays a small standing trickle with the station owner, matching the commerce trickle Phase 8b already pays for trading. Data is an intangible: it costs no cargo space and is not lost on death (the ledger is knowledge, not freight) — losing a hold full of derelict loot is penalty enough.

**Map screens (game layer, `game/src/map_screen.cpp` + a `sol::ui::MapPanel` contract in `screens.hpp`).** `M` opens the map from flight or from a station and `M`/Esc closes it; it is a `GameState::Map` beside `Docked` in the `main.cpp` state machine — it owns the keyboard but, like `Docked`, **does not stop the clock**, because a galaxy that pauses while you read the map is not the galaxy this game is selling. A tab strip carries the two views, and both are drawn with the existing `DrawList` primitives (`addArc`/`addCircle` from the HUD work already covers the node glyphs):
- **Galaxy map** — the lane graph projected from `SystemSpec::mapPosition` with pan and zoom, region rings, owner color from `GameFaction::color`, and knowledge state in the node glyph (unknown systems are absent entirely; charted are hollow and unnamed beyond their name; visited are filled; surveyed carry a completion tick). Selecting a node opens a side panel with what you actually know about it, and plotting a route runs the existing `sim::routeBetween` and lights the lane chain; the HUD then carries a "next hop" line naming the gate to take. No auto-jump.
- **System map** — a top-down of the current system's playfield (star, planets, stations, gates, discovered signals) at a clamped log radius so an AU-scale star and a 1e8 m station are legible on one screen. Selecting a marker selects the nav target; activating it hands off to the existing autopilot.

**HUD & input.** The flight HUD grows a compact **contacts** block (unresolved contacts by bearing and range, the resolved-site count for the system), a pulse cooldown ring on the crosshair, a target-scan progress arc while a scan is running, the `[G] SALVAGE` prompt in the existing prompt slot, and the plotted route's next hop. New keys are `R` (pulse) and `M` (map), both of which are free today; both go through the existing gameplay-key guard so they mean nothing on a screen.

**Data model.** `FitStat` gains `ScanRange` and `ScanSpeed` (`scan_range_add/_mul`, `scan_speed_add/_mul`), so scanners are ordinary utility modules under the Phase 8a power/mass budget and a scanner is a real fitting choice rather than a flag; `ShipDef` gains `scan_range` and `scan_speed` base stats. `game/data/modules.toml` gains a scanner line per tier, and a new `[[signal]]`-flavored tuning block lives in `SurveyParams` defaults (base ranges, pulse cooldown, per-region signal counts and values) — as with the deductible/resale fractions, these start as game-side constants and move to data when a settings def exists.

**Lua & console.** Loot composition is content, so it follows the `faction_think`/`mission_board` pattern: on resolution C++ calls `signal_loot(kind, system, region, roll)` with the signal's own seeded roll as the only entropy, the script posts a loot table through `sol.set_loot{...}`, and C++ validates it against caps (known commodity ids, unit ceilings, sellable module ids) with a built-in default table when no script answers. `signal_found(kind, system)` fires for flavor. Console: `sol.knowledge`, `sol.signals`, `sol.scan` (force-resolve the current target — dev pacing), `sol.pulse`, `sol.survey_ledger`, `sol.sell_survey`, `sol.route`, and `sol.chart` (dev cheat: mark a system visited).

**Save v7.** Body gains the survey block: per-system knowledge state, per-signal discovered/resolved/emptied bits, the unsold ledger, and the plotted route. Layout re-derives from galaxy + defs and load fails on a count mismatch — the economy rule every sibling sim follows — and the version bump follows the v4/v5/v6 compatibility policy (old saves rejected cleanly, not migrated).

**Out of scope (named so they are not half-built).** Remote market intel — remembered prices with staleness on the galaxy map — is the natural next lever on this machinery and the fix for the Phase 7 "remote prices are invisible" caveat, but it is not in v1. Neither are survey/investigate mission objectives (a new `ObjectiveKind` on `MissionSim`), planetary/atmospheric scanning (GDD §9 non-goal), scannable NPC cargo, or exploration-gated unlocks. Auto-jump route flying stays rejected on `decisions/005` grounds.

**Exit**: from a standing start, pulse in an unexplored fringe system, fly to a contact, watch the target scan resolve it into a derelict, empty it, and sell the cargo — and see the survey ledger pay separately at the same station, more than the same data pays in the core; a system with every body and site resolved reads `Surveyed` on the galaxy map and pays its completion bonus once; the galaxy map shows exactly what the player has earned the right to see — unknown systems absent, systems charted by standing at a gate hollow and contentless, visited systems filled with owner and stations — and plotting a route across four jumps lights the lanes and names the next gate on the HUD; the system map places every known marker legibly at both AU and 1e8 m scale and hands a selection to the autopilot; the whole loop is operable on the keyboard alone; scanning a fresh galaxy twice from the same seed produces identical signals, positions, and loot; save/reload restores knowledge, per-signal state, ledger, and plotted route exactly; `SurveySim` is unit-tested like its siblings (generation determinism, one-way transitions, value math, tick-for-tick save/load) with map projection and culling covered in `ui.unit`, all suites green and zero warnings. *(Verified live 2026-08-16, seed 1701, across seven scripted sessions: six gate hops out of the core reached **Praioos** (frontier, Freight Guild, 3 sites), where a fitted Survey Scanner Mk1 widened the pulse to a logged "within 400000 km" and four pulses found all three sites — the contacts list reading "1: unidentified contact, 313720 km / 2: 557524 km / 3: 516980 km" and the Lua `signal_found` hook printing "[scan] contact in Praioos" once per new contact.
