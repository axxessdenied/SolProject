# 009 — Audio: ogg approved, vendored, and confined to the cooker

- **Date**: 2026-08-18
- **Status**: accepted

## Context

Engine plan §5 open question 5, due at Phase 8: the audio decoder is a
dependency decision, and AGENTS.md §5 requires explicit user approval
before any library joins the four already approved (Vulkan, glslang,
Lua, Dear ImGui). Nothing has been added since the project began.

Phase 8t was picked from the roadmap with the board empty. Audio is
total greenfield: zero occurrences of `audio` in `game/src`, and zero
occurrences of `audio` or `sound` in the GDD. §2.10's promised stub —
"so gameplay code can post sound events into a void" — was never built.

The choice was put to the user as three options, framed by what the code
makes cheap: synthesise everything and stay dependency-free; approve an
ogg decoder; or write an in-repo codec. Decided by the user
2026-08-18: **approve the decoder.**

## Decision

**A vendored stb_vorbis-class ogg decoder is approved, under the terms
`third_party/` already imposes** — never modified in place, never
linked against `sol_options`, excluded from formatting and linting.

**It links to the cooker only.** Phase 8t's agreed scope is one-shot
cues plus a single player-engine loop, and a one-shot does not need
streaming. `.ogg` and `.wav` sources are both decoded at cook time into
PCM inside `.saud`, so **the shipping binary carries no decoder at all**
and the runtime has no third-party code in its audio path.

The `.saud` header carries a `codec` field from version 1, so moving
the decoder into the runtime for streamed music is an additive change
that needs no second approval.

## Alternatives considered

**Synthesise everything, zero dependencies** — every source asset in
this repo is already generated by `tools/scripts/gen_assets.ps1` (deleted at
Phase 26; the nine cues are `assets/sounds/*.snd` documents now, and the
sentence stands as it was written — synthesis is still where the content comes
from, and this decision is still what allows a recorded file beside it), so
this was the option most consistent with existing practice, and it
would have closed §5.5 as "not needed". Rejected because it permanently
locks the game's sound to what a PowerShell synthesiser can produce;
the approval's real value is the freedom to drop a recorded file in.

**Write an in-repo decoder** — ogg Vorbis from scratch is a
multi-thousand-line item (MDCT, Huffman, floor/residue decode) and
would dwarf the phase that needs it. IMA-ADPCM was the realistic
in-repo option at roughly 4:1, but it compresses without buying the
ability to accept ordinary audio files, which is the point.

**Vendor the decoder into the runtime** — needed for streamed music,
and rejected only for *now*: with one-shot cues, ten short cues cost
about 3 MB of PCM in memory, so streaming would be complexity bought
for nothing. The `codec` field is the hinge that keeps this reversible.

## Consequences

- **AGENTS.md §5's dependency table gains its first row since the
  project began.** The precedent to guard: this was approved for a
  named, bounded use, not as a general opening of the policy.
- The cooker gains a third-party link; the engine and game do not.
  **If a future change puts stb_vorbis in the runtime, this record is
  the thing that has to be revised** — the row says "cooker only" and
  it must stay true or be changed deliberately.
- **The decoder is not content.** Approving it supplies no audio files.
  Phase 8t still synthesises its placeholder cue set through
  `gen_assets.ps1`, and any cue can later be replaced file-for-file by
  a recorded `.ogg`. Sourcing and licensing real audio remains an open
  practical problem this decision does not solve.
- Music and streaming stay out of scope; §2.10 and the Phase 8t spec
  both say so, and both name the `codec` field as the way back in.
